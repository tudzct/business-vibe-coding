# Audit Generation Metrics

Follow [database policy](../../../docs/00-context/engineering/DATABASE-SCHEMA.md). Before assessment, run `<python-executable> .codex/scripts/validate_experiment_configuration.py <pinned-configuration.json>`; this rechecks every frozen API path/identity/SHA-256. Before runtime observation and after verification run `<python-executable> .codex/skills/gen-coding-prompt/scripts/database_baseline.py --configuration <pinned-configuration.json>`. Inspect entity/query compatibility with the pinned DBML and absence of generated DDL/migrations/schema sync (`synchronize` remains false). Authorized data changes are permitted; schema changes are not. Never replace expected hashes to accept drift, reset data/volumes or change schema to make audit pass. On failure retain partial evidence and report the input/runtime blocker without fabricating verdicts. Verify migration history/head as well as both hashes. Within a run, use `up -d --build --no-deps backend frontend` for authorized rebuilds; never start the migration service. A schema change requires researcher setup and a new configuration/run under the database policy.

A direct audit command authorizes an initial audit with no separate result confirmation. Require closed source telemetry and exact frozen baseline/configuration/source identity. This skill may also run as an explicitly authorized subordinate verifier; that authorization comes only from the active caller contract.

After initial BR/flow evidence is persisted and validated, run `advance-experiment-gate/scripts/record_command.py --run-json <canonical.json> --action audit --turn-id <actual-id>` (dry-run first) within the audit turn. It records initial completion and the validated current outcome. Do not edit source, invoke another top-level operation or request result approval. Activation is optional.

When invoked as a subordinate verifier, keep the caller's existing timer and token label through BR/flow/runtime verification and final evidence/hash/status persistence; the caller owns its endpoints. Do not open an overlapping timer. A standalone audit never starts a core generation timer.

1. Preserve requested and effective model metadata separately; never infer unavailable telemetry.
2. Read the shared timing protocol. Audit-only turns use workflow-only token label `audit`. Audit does not capture generation time or extract live-turn tokens. Explicit measurement commands own canonical `metrics`; preserve that block byte-for-value when saving audit results.
3. Preserve the immutable initial assessment before any repair.
4. Read `ordered_br_ids` from the frozen BR baseline as the complete ordered audit inventory and denominator. Assess every listed BR exactly once from actual integrated-runtime behavior as `met`, `unmet` or `not_evaluable`; use the special whole-inventory state `execution_blocked` only under the generated-source blocker rule below. Resolve each OCL or natural-language requirement from the checksum-pinned frozen UC. Static source/configuration/build findings may diagnose a defect but cannot by themselves establish a conclusive BR verdict. Every normal BR row references the runtime observation IDs used for its decision.
   If the researcher supplies a verdict, resolves `not_evaluable`, or challenges a `met`/`unmet` result, process it through the same follow-up operation used for flow results. One response may cover BRs, flows or both. A direct verdict is researcher-attributed; a request to check again triggers an evidence-backed LLM re-audit. Unmentioned results retain the audit verdict. Save the whole response atomically and preserve immutable assessment snapshots.
5. In this same audit operation, invoke `audit-flow-accuracy` for the same UC/run/source revision using the rubric resolved from checksum-pinned configuration. Read its per-flow procedure and schema. Read `ordered_flow_ids` as the complete ordered flow inventory and resolve each listed flow from the checksum-pinned frozen UC. Runtime-v2 requires actual integrated-runtime observations for conclusive BR and Flow verdicts produced by AI audit or LLM re-audit. A direct researcher verdict remains explicitly researcher-attributed and does not acquire fabricated runtime evidence. Reuse the frozen flow baseline and preserve initial evidence. A subordinate final-stage verification observes every flow on the supplied final source with fresh evidence under the same rubric. When the source is unchanged and a validated terminal projection is permitted, retain the original assessment identity and evidence rather than fabricating a second observation. Missing target evidence after an executable runtime leaves only the affected result `not_evaluable`.
   If an evidenced defect in the generated source prevents the integrated system from running, record that one root cause once in canonical `defects`, set `blocks_execution: true`, reference it from `execution_blocker_defect_ids`, and mark every frozen BR and Flow `execution_blocked`. Do not use this state for a missing Docker daemon, operator setup problem or ambiguous cause; retain the existing input/environment blocker handling instead. `execution_blocked` is not researcher-overridable through audit follow-up. Figma/UI accuracy is operator-managed and must not be calculated or mutated here.
6. Record every evidenced first-pass/final root cause once in canonical `defects` as category `business_rule`, `flow` or `technical`, with its fingerprint, trigger, description, all affected IDs, execution-blocking flag, immutable evidence, source revision, stage and status. Do not duplicate one root cause merely because it affects several BRs/Flows. Every AI-audited BR `unmet` and Flow `incorrect` is covered by an affected ID in a defect; a direct researcher correction remains attributed to the researcher and does not manufacture a canonical defect or runtime proof. Technical/build/backend/frontend/runtime/API/integration failures remain defects even when they are outside a BR or Flow. `not_evaluable` is not itself a defect.
7. Validate BR-ID equality, flow identity/totals, defect coverage, timing, tokens and source checksum using `scripts/calculate_metrics.py`.
8. Persist canonical JSON without overwriting canonical telemetry or operator-managed UI fields. Print one combined BR/flow/defect summary, including execution-blocked counts. Do not calculate a Business Rule acceptance percentage or invoke reporting/export operations. For a terminal-stage verification, freeze `business_rules.source_revision` and persist the evidence-backed terminal run status.

Do not create/run tests or claim unsupported correctness.

When normal results are partial or challenged, preserve known metrics and offer one combined researcher verdict or bounded LLM re-audit. Save either path with attribution through the existing follow-up mechanism, report the resulting statuses and stop. A later inconclusive attempt never erases an earlier conclusive verdict. Keep source/evidence requirements and original assessments immutable. Optional UI scores never block this operation. Do not export data or create/run tests.
