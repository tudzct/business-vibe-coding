# Audit Generation Metrics

Follow [database policy](../../../docs/00-context/engineering/DATABASE-SCHEMA.md). Before assessment, run `<python-executable> .codex/scripts/validate_experiment_configuration.py <pinned-configuration.json>`; this rechecks every frozen API path/identity/SHA-256. Before runtime observation and after verification run `<python-executable> .codex/scripts/database_baseline.py --configuration <pinned-configuration.json>`. If and only if database validation exits with `DOCKER_ACCESS_REQUIRED`, rerun the identical read-only command once with host approval; denied approval or a failed retry blocks, and no other validation error is elevated or retried. Inspect entity/query compatibility with the pinned DBML and absence of generated DDL/migrations/schema sync (`synchronize` remains false). Authorized data changes are permitted; schema changes are not. Never replace expected hashes to accept drift, reset data/volumes or change schema to make audit pass. On failure retain partial evidence and report the input/runtime blocker without fabricating verdicts. Verify migration history/head as well as both hashes. Within a run, use `up -d --build --no-deps backend frontend` for authorized rebuilds; never start the migration service. A schema change requires researcher setup and a new configuration/run under the database policy.

A direct audit command authorizes an initial audit with no separate result confirmation. Require closed source telemetry and exact frozen baseline/configuration/source identity. A direct initial audit also requires an independent evaluation context: if the active conversation contains source-generation execution for this exact run, stop before loading assessment inputs or writing results and report that the initial audit must run in an independent evaluation context. This skill may also run as an explicitly authorized subordinate verifier; that authorization comes only from the active caller contract and is exempt from the independent-context requirement.

After initial BR/flow evidence is persisted and validated, run `advance-experiment-gate/scripts/record_command.py --run-json <canonical.json> --action audit --turn-id <actual-id>` (dry-run first) within the audit turn. It records initial completion and the validated current outcome. Do not edit source, invoke another top-level operation or request result approval. Activation is optional.

When invoked as a subordinate verifier, keep the caller's existing timer and token label through BR/flow/runtime verification and final evidence/hash/status persistence; the caller owns its endpoints. Do not open an overlapping timer. A standalone initial audit is outside workflow measurement and never starts a core generation timer.

1. Preserve requested and effective model metadata separately; never infer unavailable telemetry.
2. Read the shared timing protocol. A standalone initial audit has no workflow token label and is excluded from workflow telemetry. Audit does not capture generation time or extract live-turn tokens. Explicit measurement commands own canonical `metrics`; preserve that block byte-for-value when saving audit results. A subordinate verifier retains the active caller's `repair` label.
3. Preserve the immutable initial assessment before any repair.
4. Read `ordered_br_ids` from the frozen BR baseline as the complete ordered audit inventory and denominator. Resolve each OCL or natural-language requirement from the checksum-pinned frozen business-rule specification referenced by that baseline. Assess every listed BR exactly once from actual integrated-runtime behavior as `correct`, `incorrect` or `not_available`. Static source/configuration/build findings may diagnose a defect but cannot by themselves establish a conclusive BR verdict, except under the operational completion rules below. Every normal conclusive BR row references the runtime observation IDs used for its decision. Every `incorrect` BR names the canonical defect IDs that caused it; every `not_available` BR records the exact unavailable reason.
   If the researcher supplies a verdict, resolves `not_available`, challenges a result or reports a technical/UI issue, process it through the same follow-up operation used for flow results. Accept the single five-field researcher format defined in `audit-flow-accuracy/references/follow-up-measurement.md`; `Result` is always `correct` or `incorrect`, and one response may contain multiple items. A direct verdict is final and researcher-attributed; do not verify whether the researcher is correct. Infer the canonical category and affected IDs from `Target`; for a Basic Flow target, require the exact `BF-<flow>.<step>` ID from the frozen UC, resolve it to its parent `BF-<flow>` in `ordered_flow_ids`, and record the defect against that parent Flow without treating the step as another Flow. Use `Description` and `Evidence` as the attributed repair facts, and derive all internal fingerprints, source revision, paths and checksums. Never ask the researcher to copy the Basic Flow step text, author JSON or supply other internal fields. An `incorrect` result or reported technical/UI issue creates a normalized open initial defect before prompt generation; `correct` creates no defect. Unmentioned results otherwise retain the audit verdict. Save the whole response atomically and preserve immutable assessment snapshots.
5. In this same audit operation, invoke `audit-flow-accuracy` for the same UC/run/source revision using the rubric resolved from checksum-pinned configuration. Read its per-flow procedure and schema. Read `ordered_flow_ids` as the complete ordered flow inventory and resolve each listed flow from the checksum-pinned frozen UC. Runtime-v2 requires actual integrated-runtime observations for conclusive BR and Flow verdicts produced by AI audit or LLM re-audit. A direct researcher verdict remains explicitly researcher-attributed and does not acquire fabricated runtime evidence. Reuse the frozen flow baseline and preserve initial evidence. A subordinate final-stage verification observes every flow on the supplied final source with fresh evidence under the same rubric. When the source is unchanged and a validated terminal projection is permitted, retain the original assessment identity and evidence rather than fabricating a second observation. Missing target evidence after an executable runtime leaves only the affected result `not_available`.
   A proven generated-source `technical` or functional `ui` defect propagates `incorrect` only to its affected BRs and Flows. If it prevents the whole integrated system from running, set `blocks_execution: true`, cover the complete frozen BR/Flow inventories, reference it from `execution_blocker_defect_ids`, mark every frozen BR and Flow `incorrect`, and set Flow accuracy to `0%`. Preserve the defect IDs as the reason for those verdicts. Do not apply this rule to a missing Docker daemon, operator setup problem or ambiguous cause unless the researcher explicitly makes the final classification. Blocker-derived verdicts are not subsequently researcher-overridable through audit follow-up.
6. Record every evidenced first-pass/final root cause once in canonical `defects` as category `business_rule`, `flow`, `technical` or `ui`, with its fingerprint, trigger, description, all affected IDs, execution-blocking flag, immutable evidence, source revision, stage and status. `ui` is limited to functional interaction, navigation, state or frontend failures that prevent required behavior; cosmetic Figma differences remain researcher-managed. Do not duplicate one root cause merely because it affects several BRs/Flows. Every `incorrect` BR/Flow references at least one open defect through `caused_by_defect_ids`, and every affected BR/Flow named by an open functional defect is `incorrect` and references that defect. A direct researcher correction to `incorrect` creates an attributed canonical defect from the researcher's supplied repair facts but never fabricates independent runtime proof. `not_available` is not itself a defect and must remain pending until the researcher supplies `correct` or `incorrect` or authorizes bounded remeasurement.
7. Validate BR-ID equality, flow identity/totals, defect coverage, timing, tokens and source checksum using `scripts/calculate_metrics.py`.
8. Persist and validate canonical Audit results only. Defects Handoff construction is outside this Audit-only revision and must not run until its separate contract is updated for the normalized result vocabulary and `ui` category.
9. Persist canonical JSON without overwriting canonical telemetry or operator-managed Figma/UI accuracy fields. Print one combined BR/Flow/defect summary. For every `incorrect` target print its causing defect IDs, category and description; for every `not_available` target print its unavailable reason and the required researcher resolution. Also report whether execution was blocked, its scope and the blocking defect count. Do not calculate a Business Rule acceptance percentage or invoke handoff, reporting or export operations. For a terminal-stage verification, freeze `business_rules.source_revision` and persist the evidence-backed terminal run status.

Do not create/run tests or claim unsupported correctness.

When normal results are partial or challenged, preserve known metrics and offer one combined researcher verdict or bounded LLM re-audit. Save either path with attribution through the existing follow-up mechanism, report the resulting statuses and stop. A later `not_available` attempt never erases an earlier conclusive verdict. Keep source/evidence requirements and original assessments immutable. Researcher-managed Figma/UI scores never block this operation. Do not export data or create/run tests.
