# Metric rubric

## Business Rule results

The frozen ordered BR list is the denominator. Each BR receives one terminal status:

- `correct`: an integrated-runtime observation demonstrates the complete rule; **if and only if** the rule cannot be audited at runtime (with the exact runtime limitation documented), `correct` may be inferred from conclusive static inspection of generated source/configuration/build code.
- `incorrect`: an integrated-runtime observation OR conclusive static inspection of generated source/configuration/build code demonstrates that the rule fails, is omitted/contradicted or cannot be completed because of a proven generated-source defect.
- `not_evaluable`: runtime auditing is not possible or incomplete and neither runtime observation nor static code inspection can conclusively establish `correct` or `incorrect`; state the exact limitation.

Prompt prose alone is not evidence. Whenever runtime auditing is possible, `correct` requires actual integrated-runtime observation; static source/configuration/build inspection may establish `correct` **if and only if** runtime observation cannot be performed for that target and both the runtime limitation and inspectable static evidence are recorded. Conclusive static source/configuration/build findings may also establish `incorrect` (and diagnose/classify its canonical defect) when generated code demonstrably omits, violates, contradicts or prevents the required rule or flow, provided inspectable static evidence and the causing canonical defect IDs are recorded instead of claiming runtime observation. Under the operational completion rule, a proven generated-source technical/UI defect makes every affected BR and Flow `incorrect`; a system-wide blocker affects the complete frozen inventories and produces Flow accuracy `0%`. Every affected result references the causing canonical defect IDs instead of claiming successful runtime observations. Initial and final snapshots contain exactly the baseline BR IDs in order and their totals match.

Canonical `defects` records one root cause once per source stage as `business_rule`, `flow`, `technical` or `ui`. Functional UI defects prevent required interaction, navigation, state transition or frontend integration; cosmetic Figma differences remain researcher-managed. Every `incorrect` BR/Flow contains `caused_by_defect_ids`, and every affected target named by an open functional defect is `incorrect` and references that defect. A direct researcher correction to `incorrect` creates an attributed defect from the supplied repair facts without inventing runtime proof; `correct` creates no defect. `not_evaluable` is not a defect and requires an `unavailable_reason` plus researcher resolution or bounded remeasurement. A generated-source defect with `blocks_execution: true` produces system-wide `incorrect` verdicts and a separate execution-blocked note; environment/researcher setup failure or ambiguous cause does not unless the researcher makes the final classification.

Accepted BR reporting follows `accepted-br-audit-results-v1`. Researcher verdicts and evidence-backed LLM re-audits are append-only follow-ups tied to the immutable parent snapshot and source revision. The latest conclusive result per BR in the active stage is selected; a later `not_evaluable` result does not erase an earlier `correct` or `incorrect`. Researcher verdicts retain attribution and are never presented as independent runtime evidence.

## Supporting metrics

- First-pass audit and automatic verification within authorized repair run `audit-flow-accuracy` against the frozen Basic/Main, Alternative and Exception Flow denominator. Each flow has equal weight; steps only determine whether their parent flow can complete. No separate final-audit gate is required.
- Figma/UI visual accuracy is researcher-managed. Functional UI failures are canonical `ui` defects; Audit never calculates, validates or overwrites the manual visual score.
- Complexity records actors, main steps, alternate/exception flows, entities, integrations, Business Rules and UI states.
- Time comes from automatic timezone-qualified ISO/epoch pairs; tokens come only from telemetry.
- Explicit close/finalize commands invoke the measurement engine, which owns canonical `metrics`; Audit preserves it while validating BR/flow evidence.
- Export input, cached input, output, reasoning output and total separately for Prompt Generation, Source Generation, Sub-prompt Generation, Repair and the full workflow, plus captured seconds, selected turn count and observable tool-call count. Cached/reasoning are subsets, never added again. Do not publish fresh input, usage-update count, estimated call counts, money cost or a legacy three-phase subtotal. Missing telemetry is null with a reason.
- Workflow seconds = Prompt execution + first-pass Source execution + complete sub-prompt generation + the complete source-correction invocation at the shared START/END boundaries. Configuration, approval, dataset resolution, separate audit/runtime/finalization and Measure/report work are excluded from time. Capture endpoints live; aggregate after completion. Never substitute UI duration, whole-chat elapsed time or missing endpoints.
- Record generation, audit and each repair model independently. Use the exact [approved prompt](../../../../docs/02-construction/coding-prompts/%3CUC-ID%3E-coding-prompt.md) and source baseline pinned to the active run.
- The first-pass audit response and the repair response print BR and flow summaries. Researcher-managed UI and manual Excel fields remain untouched.
