## Autonomous Execution and Self-Correction Directives

To guarantee seamless, fully autonomous execution without human operator interruption:

1. **Autonomous Operation**: Never halt, ask questions, or request confirmation from the operator during the repair loop. Process the complete fixed prompt set in one invocation. For each defect, run consecutive correction-and-verification attempts until it is resolved or its tenth attempt is completed, then continue to the next defect.
2. **Phase Isolation**: Do NOT use `record_flow_followup.py` during Repair. That tool is exclusively for initial pre-repair challenge audits. During Repair, verification is performed strictly through direct runtime observation, assessment assembly via `assemble_repair_assessment.py`, and subordinate audit scoring via `score_flow_accuracy.py`. Do NOT request or require `request_turn_id` from the operator.
3. **Runtime Observability**:
   - Choose runtime actions from the current fixed sub-prompt, current application and actual current-attempt runtime state. Do not infer an action, role, route, permission state or expected result from an ID prefix.
   - Use the runtime tool appropriate to the behavior being verified, and save each sanitized observation under `runs/<RUN-ID>/flow-accuracy/evidence/<assessment-id>/<observation-id>/`.
   - Record the actual flow and BR snapshot plus the current immutable-defect verdict in `verification-results.json`. It must identify the exact UC, run, assessment, ordered flow inventory, ordered BR inventory and the one defect under verification; every verdict must carry its actual evidence path. Missing evidence remains unresolved or not evaluable and must never be synthesized as successful.
4. **Automated Schema v2 Assembly**:
   - Do NOT hand-edit Schema v2 JSON files. Always run the automated assessment assembly helper:
     `python .codex/skills/repair-source-code/scripts/assemble_repair_assessment.py --run-json <canonical.json> --assessment-id <assessment-id> --verification-results <verification-results.json> --defect-id <current-defect-id> --update-repairs`
     This helper clones Schema v2 structure, validates the exact frozen inventories, calculates SHA-256 for recorded runtime artifacts, sets the attempt's `source_revision_after`, and synchronizes only the evidence-backed Repair and final BR results.
   - Run the flow scorer:
     `python .codex/skills/audit-flow-accuracy/scripts/score_flow_accuracy.py --run-json <canonical.json> --assessment <assembled-assessment-path>`
   - Alternatively, execute the all-in-one autonomous verification helper:
     `python .codex/skills/repair-source-code/scripts/run_repair_cycle.py --run-json <canonical.json> --assessment-id <assessment-id> --verification-results <verification-results.json> --defect-id <current-defect-id>`
     This helper validates already-captured runtime evidence, assembles the Schema v2 assessment, synchronizes the current defect attempt, scores flow accuracy and validates the recorded sequence. It never invents runtime observations or verdicts.
5. **Self-Correction Retry Directive**:
   - If any command, build, or verification script exits with an error or validation failure, do NOT stop and report to the operator.
   - Read the traceback/error directly, correct the offending source code or recapture invalid evidence, and retry the failed command up to 3 times within the current defect attempt. Never edit evidence to manufacture a passing result.
   - If the current defect remains unresolved after attempt N, use the verifier result only to decide that the same fixed target requires another attempt. Technical diagnostics may explain why the current implementation failed, but they must not add or rewrite requirements. Derive attempt N+1's strategy from the same fixed sub-prompt and then-current source and proceed without pausing.

## Standard Execution Sequence

1. Freeze the initial inventory byte-for-byte. Across all attempts never add, remove, merge, split, recategorize or rewrite an initial defect, fingerprint, affected-ID set or prompt. `blocks_execution: true` is only a priority flag on one of the three canonical categories: `technical`, `business_rule` or `flow`; it is not a fourth category. Do not generate supplemental prompts or expand the inventory during Repair. A newly observed issue outside the fixed inventory may be reported at the end, but it must not be repaired, added to the loop or used to generate another prompt.
2. Process defects one at a time in fixed prompt order. For the current defect, apply only its completed sub-prompt, then run subordinate verification for that defect. If verified `resolved`, move to the next defect. If `unresolved`, retry the same defect immediately with a revised strategy. After its tenth unresolved attempt, preserve that defect as terminally unresolved and continue to the next defect. Never place several defects in one attempt, revisit a resolved defect or begin the next defect before the current one is resolved or has exhausted ten attempts. A prior correction may indirectly resolve a later fixed defect; when that defect becomes current, verify it and record it resolved without making a speculative change.
3. Before the first source mutation, set `repair_status: in_progress` and capture one Repair START with `.codex/scripts/capture_timestamp.py --run-json <canonical.json> --phase repair --event start --repair-activity source_correction --segment-id <one-unique-segment-id> --source-revision sha256:<actual-64-hex>`. The helper resolves the active rollout and turn internally; never supply or guess either path or ID. Keep this single interval open through every defect attempt, permitted build/runtime check, subordinate verification and final evidence/hash/status persistence in this invocation. Append one canonical record per completed defect attempt, but never open per-defect or per-attempt timers. Increment `repair_rounds_completed` only after each attempt record is complete. Capture one Repair END with the same helper, segment ID and activity before responding, waiting for the researcher or resolving an external blocker. Never finalize tokens in this turn.
4. After each correction attempt, rebuild and restart containers with `docker compose up -d --build --no-deps backend frontend`. Then execute subordinate verification autonomously against the current application. Save sanitized runtime evidence and actual deployment details under `runs/<RUN-ID>/flow-accuracy/evidence/<assessment-id>/`; record the exact evidence-backed flow/BR snapshot and the one current fixed-defect verdict in that assessment's `verification-results.json`; then execute `python .codex/skills/repair-source-code/scripts/assemble_repair_assessment.py --run-json <canonical.json> --assessment-id <assessment-id> --verification-results <verification-results.json> --defect-id <current-defect-id> --update-repairs` and `python .codex/skills/audit-flow-accuracy/scripts/score_flow_accuracy.py --run-json <canonical.json> --assessment <assessment-path>`. The execute-only helpers validate frozen inventories internally. Preserve all initial evidence without opening it. Verification must not append a defect, create a new repair target, change the fixed inventory or generate another prompt file. Complete verification before counting the attempt or deciding whether to retry the same defect or advance to the next one; never open a separate Audit timer or count it twice.
5. After every fixed defect has reached a terminal result, preserve the latest evidence-backed BR/Flow snapshot as the post-Repair result. Finish successfully only when every fixed defect is resolved, every BR is `met`, every Flow is `correct`, Flow Accuracy is `100%`, and no technical or execution-blocking failure remains. Persist `repair_status: completed`, the final source revision/evidence and terminal `run_status: complete`.
6. If one defect remains unresolved after attempt 10, do not run attempt 11 and do not stop the complete invocation early. Mark only that defect terminally unresolved and continue through all remaining prompts. After every fixed defect has been processed, if any defect is unresolved or the final BR/Flow snapshot is not fully passing, persist `repair_status: unresolved` and terminal `run_status: stopped`. Do not fabricate `met`, `correct` or resolution.
7. Stop earlier with `repair_status: blocked` and terminal `run_status: blocked` only when correction requires a requirement/API/ownership/destructive-data decision, a frozen-input or schema change, or another action outside Repair authority. A schema blocker never authorizes an in-run DBML/schema/index/constraint/grant/migration change. Capture the actual END, preserve partial evidence and report the exact blocker. For Docker rebuilds use `--no-deps backend frontend` so the setup migration service cannot run.
8. Before returning, run `scripts/validate_repair_rounds.py --run-json <canonical.json> --prompt-dir <repair-prompt-directory> --final`, then execute `.codex/skills/audit-generation-metrics/scripts/calculate_metrics.py <canonical.json>` as an execute-only final summarizer. Print its pre/post-Repair summary containing total attempts, attempts and terminal status for every fixed defect, Repair status, BR counts, Flow counts/accuracy, resolved/unresolved technical-defect counts and the execution-blocked note. Preserve the initial Audit snapshot unchanged. Do not print an `Open defects` field or invoke another top-level operation.

Do not create or run tests.
