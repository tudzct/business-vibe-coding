# Repair Source Code

Apply the [shared operational constitution](../../../AGENTS.md#shared-operational-constitution).

Accept exactly one repairs directory containing the complete validated `repair-<NNN>-<DEFECT-ID>.md` set and read the [repair contract](references/repair-contract.md). Read each completed sub-prompt in full and perform its required correction for its immutable initial defect. Canonical evidence, validated project inputs and current source provide facts and technical constraints. The model chooses the concrete repair strategy and may revise that strategy between rounds. If a prompt conflicts with a pinned input or immutable technical boundary, report the exact conflict and stop instead of silently deviating.

Read the pinned DBML and [database policy](../../../docs/00-context/engineering/DATABASE-SCHEMA.md). Before repair START run `<python-executable> .codex/scripts/validate_experiment_configuration.py <pinned-configuration.json>` to recheck every frozen API path/identity/SHA-256, then run `<python-executable> .codex/scripts/database_baseline.py --configuration <pinned-configuration.json>`. If and only if database validation exits with `DOCKER_ACCESS_REQUIRED`, rerun the identical read-only command once with host approval; denied approval or a failed retry blocks, and no other validation error is elevated or retried. Failure blocks correction without replacing inputs. Repair may fix entities, queries and services to use existing structure and perform authorized DML. It cannot change DBML, schema, indexes, constraints, grants or migrations, reset a volume or enable synchronization. Child audit rechecks the same pins after verification while the repair timer remains open.

Invoking `$repair-source-code <repair-prompt-directory>` authorizes correction of the complete immutable defect inventory represented by that directory. Consume the validated canonical run, accepted audit results, immutable initial defect inventory and supplied prompt artifacts as handoff artifacts; do not read the prompt-generator skill instructions or its private template. Resolve the exact UC/run with source telemetry closed and a saved initial BR/Flow/defect audit. Run `scripts/validate_repair_rounds.py --run-json <canonical.json> --prompt-dir <repair-prompt-directory>` before authorization and require an exact one-to-one prompt/defect match plus the recorded prompt-set handoff. Require conclusive accepted BR/Flow verdicts; blocker-derived `unmet`/`incorrect` results are eligible when their generated-source execution blocker is pinned. Run `advance-experiment-gate/scripts/record_command.py --run-json <canonical.json> --action repair --turn-id <actual-id>` (dry-run first), then begin the complete correction loop in this same work turn without another confirmation. Retain an existing recorded authorization if already recorded; never reopen terminal runs.

Saving either researcher or LLM follow-up results alone does not authorize repair. Acknowledge saved results and wait for this subsequent command. Normal `not_evaluable` BRs or flows block new repair authorization. An execution-blocking technical defect permits correction of that evidenced blocker without a researcher verdict; execution blocking remains an operational note rather than a fourth BR/Flow verdict. Accept attributed normal researcher verdicts without fabricating or requiring a second LLM proof. Activation is optional; concrete source/schema/runtime prerequisites remain.

1. Freeze the initial inventory byte-for-byte. Across all rounds never add, remove, merge, split, recategorize or rewrite an initial defect, fingerprint, affected-ID set or prompt. `blocks_execution: true` is only a priority flag on one of the three canonical categories: `technical`, `business_rule` or `flow`; it is not a fourth category. Do not generate supplemental prompts or expand the inventory during Repair.
2. Execute at most ten global rounds autonomously within this single repair turn. In round 1, address every initial defect using its fixed sub-prompt, prioritizing defects with `blocks_execution: true` and then retaining canonical order. In later rounds, address every defect not yet verified as resolved: use the fresh audit assessment, runtime traces and failure evidence of the preceding round as an internal feedback prompt to synthesize a revised correction strategy. A correction may resolve several defects, but each fixed defect remains independently verified. The model controls file choice within allowed scope, implementation approach, command sequence and revised strategy between rounds; the contract fixes targets and boundaries, not a deterministic patch. Continue this correction-and-audit loop autonomously without stopping or waiting for operator intervention until full resolution or round 10 exhaustion.
3. Before the first source mutation, append the first canonical in-progress round record described by the repair contract, set `repair_status: in_progress`, and capture one Repair START with `.codex/scripts/capture_timestamp.py --run-json <canonical.json> --phase repair --event start --repair-activity source_correction --segment-id <one-unique-segment-id> --source-revision sha256:<actual-64-hex>`. The helper resolves the active rollout and turn internally; never supply or guess either path or ID. Keep this single interval open through every correction round, permitted build/runtime check, subordinate audit and final evidence persistence in this invocation. Continue to append and complete canonical round records, but never open per-round timers. Increment `repair_rounds_completed` only after each round record is complete. Capture one Repair END with the same helper, segment ID and activity before responding, waiting for the researcher or resolving an external blocker. Never finalize tokens in this turn.
4. After each round's corrections, rebuild and restart containers with `docker compose up -d --build --no-deps backend frontend`. Then execute the subordinate audit autonomously: directly observe the running runtime using available tools (e.g. `curl.exe` for HTTP endpoints/headers, headless browser CLI like `& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --headless --dump-dom <url>` for UI states, and container inspection for health/logs). Populate that round's provisional source revision, write the sanitized runtime observations and trace files (`action-*.json`, `trace.json`) under `runs/<RUN-ID>/flow-accuracy/evidence/<assessment-id>/<observation-id>/`, and execute `python .codex/skills/audit-flow-accuracy/scripts/score_flow_accuracy.py --run-json <canonical.json> --assessment <assessment-path>` to persist fresh integrated-runtime evidence and per-defect `resolved`/`unresolved` results. Preserve all initial BR/Flow/defect evidence. For final-stage defect coverage, the verifier uses only this round's unresolved members of the immutable initial inventory; it must not append a final-stage defect, create a new repair target, change the initial inventory or generate another prompt file. Complete this verification before deciding whether another round is needed. If defects remain unresolved and round limit is not reached, feed the failed observations directly into the next round's strategy without stopping; never open a separate Audit timer or count it twice.
5. Finish successfully as soon as all fixed defects are verified resolved, every BR is `met`, every Flow is `correct`, Flow Accuracy is `100%`, and no technical or execution-blocking failure remains. Persist `repair_status: completed`, the final source revision/evidence and terminal `run_status: complete`.
6. If round 10 ends without satisfying the success condition, stop without an eleventh round. Persist the remaining fixed defects as unresolved in repair results, preserve the evidence-backed final BR/Flow verdicts, set `repair_status: unresolved` and use terminal `run_status: stopped`. Do not fabricate `met`, `correct` or resolution.
7. Stop earlier with `repair_status: blocked` and terminal `run_status: blocked` only when correction requires a requirement/API/ownership/destructive-data decision, a frozen-input or schema change, or another action outside Repair authority. A schema blocker never authorizes an in-run DBML/schema/index/constraint/grant/migration change. Capture the actual END, preserve partial evidence and report the exact blocker. For Docker rebuilds use `--no-deps backend frontend` so the setup migration service cannot run.
8. Before returning, run `scripts/validate_repair_rounds.py --run-json <canonical.json> --prompt-dir <repair-prompt-directory> --final`. Print one final summary containing rounds used, Repair status, BR counts, Flow counts/accuracy, resolved/unresolved technical-defect counts and the execution-blocked note. Do not print an `Open defects` field or invoke another top-level operation.

Do not create or run tests.
