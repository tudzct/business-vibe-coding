# Repair Source Code

Apply the [shared operational constitution](../../../AGENTS.md#shared-operational-constitution).

Accept exactly one completed `repair-<NNN>-<DEFECT-ID>.md` path and read the [repair contract](references/repair-contract.md). Follow that bug-fixing sub-prompt closely as the primary correction instruction. The canonical defect evidence, validated project inputs and current source provide facts and technical constraints; they do not replace the supplied sub-prompt with another correction strategy. If the prompt conflicts with a pinned input or immutable technical boundary, report the exact conflict and stop instead of silently deviating.

Read the pinned DBML and [database policy](../../../docs/00-context/engineering/DATABASE-SCHEMA.md). Before repair START run `<python-executable> .codex/scripts/validate_experiment_configuration.py <pinned-configuration.json>` to recheck every frozen API path/identity/SHA-256, then run `<python-executable> .codex/skills/gen-coding-prompt/scripts/database_baseline.py --configuration <pinned-configuration.json>`. Failure blocks correction without replacing inputs. Repair may fix entities, queries and services to use existing structure and perform authorized DML. It cannot change DBML, schema, indexes, constraints, grants or migrations, reset a volume or enable synchronization. Child audit rechecks the same pins after verification while the repair timer remains open.

Invoking `$repair-source-code <sub-prompt-path>` authorizes only the correction described by that artifact. Consume the validated canonical run, accepted audit results, defect inventory and supplied sub-prompt as handoff artifacts; do not read the prompt-generator skill or its private template. Resolve the exact UC/run with source telemetry closed and a saved initial BR/Flow/defect audit. Match the prompt's defect ID, fingerprint, source revision, category and affected IDs to one evidenced initial defect. Require conclusive accepted BR/Flow verdicts; blocker-derived `unmet`/`incorrect` results are eligible when their open generated-source execution-blocking defect is pinned. Run `advance-experiment-gate/scripts/record_command.py --run-json <canonical.json> --action repair --turn-id <actual-id>` (dry-run first), then begin correction in this same work turn without another confirmation. Retain an existing recorded authorization if already recorded; never reopen terminal runs.

Saving either researcher or LLM follow-up results alone does not authorize repair. Acknowledge saved results and wait for this subsequent command. Normal `not_evaluable` BRs or flows block new repair authorization. An execution-blocking technical defect permits correction of that evidenced blocker without a researcher verdict; execution blocking remains an operational note rather than a fourth BR/Flow verdict. Accept attributed normal researcher verdicts without fabricating or requiring a second LLM proof. Activation is optional; concrete source/schema/runtime prerequisites remain.

1. Revalidate that the supplied defect remains evidenced and applicable to the current source. If a prior correction already resolved or invalidated it, do not mutate source or create a speculative repair.
2. After planning, required resolution and authorization, create one canonical repair record for the supplied prompt and defect, preserving every prior record. Record its unique repair ID, prompt path, defect identity, category, trigger, affected IDs, initial evidence and model. Capture `repair` START immediately before executing the correction and pass that canonical `--repair-id` on both endpoints. Apply the smallest correction and keep this interval open through the integrated verification in step 3. Record exact turn/segment IDs. End before any blocker resolution, researcher wait or response; resume correction or its unfinished integrated verification with a fresh segment for the same repair ID. Never finalize tokens in this turn.
3. After the correction, invoke the audit operation only as an explicit subordinate verifier in the same repair work turn to reassess affected BRs/flows and check integration using permitted typecheck/lint/build and bounded Docker runtime observation. Before the repair phase ends, assess every frozen BR and flow on the final source, persist final results and freeze `business_rules.source_revision`. Use fresh final-stage flow evidence under the configured rubric; preserve immutable initial results. Complete this work before returning. Capture repair END only after this integrated verification and final evidence/hash/status persistence. Its elapsed time is part of Repair; do not open a second overlapping audit/runtime interval or count it twice. The entire work turn retains token label `repair`, including the subordinate audit, not the auxiliary `audit` label.
4. Report successful repair only when the correction is verified. Persist unresolved defects, unknown behavior and runtime blockers honestly; use `blocked`, `stopped` or `repair_declined` when appropriate, never fabricate `met` or `correct`. Persist terminal `run_status` when no further authorized correction remains. If another evidenced defect remains and the run is nonterminal, stop after reporting the validated repair record; a later explicit invocation supplies one different generated sub-prompt. Do not start another top-level operation automatically.
5. Stop for the researcher if the correction needs a requirement/API/ownership/destructive-data decision, if the pinned database cannot support the requirement, or after the same defect fingerprint remains for three attempts. A schema blocker never authorizes an in-run schema change. Follow the database policy: capture actual END, preserve partial evidence and require a new configuration/run after researcher migration setup. For Docker rebuilds use `--no-deps backend frontend` so the setup migration service cannot run.

Do not create or run tests.
